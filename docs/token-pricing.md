## 一、先明确计价口径

大模型 API 的账单几乎都遵循同一个结构：

```
单次请求成本 = 输入 tokens × 输入单价
             + 输出 tokens × 输出单价
             + 缓存写 tokens × 缓存写单价
             + 缓存读 tokens × 缓存读单价
```

四个容易踩的坑，按影响从大到小：

1. **输入与输出不同价，且输出通常更贵。** 按下方数据，多数模型的输入:输出比在 1:5 上下。只用输入价估算总成本，通常会低估 2~4 倍。
2. **计价单位是「每百万 tokens」。** 忘掉这个基数，会把成本误算成 1/1000000 或放大百万倍。
3. **币种不统一。** 同一张表里可能同时出现 USD 与 CNY，**不要自行换算**——汇率既非官方口径、也随时变动，混算等于制造一个查不到来源的数字。要么统一按官方币种分账，要么在内部财务口径里单独折算并标注汇率与日期。
4. **缓存是折扣，不是免费。** 缓存命中价通常是输入价的 1/10 左右（见下表备注），但它要求请求前缀稳定；前缀频繁变化会退化为全价。

## 三、把表算成一笔账（可直接套用）

以下为**纯算术示例**，输入/输出 token 量为假设值，价格取自上表，不引入任何额外假设：

**示例 A：Claude Sonnet 5，输入 3M tokens、输出 1M tokens**

```
3 × $2.00 + 1 × $10.00 = $16.00
```

**示例 B：同上用量，改为 Claude Opus 5**

```
3 × $5.00 + 1 × $25.00 = $40.00
```

同样的业务量，成本差 2.5 倍——差异全部来自模型选择，与用量无关。这就是为什么「先算清单价再选模型」比「先选模型再压缩用量」更省钱。

**示例 C：DeepSeek V4-Pro 输出 2M tokens，峰谷差异**

```
高峰：2 × ¥27.00 = ¥54.00
闲时：2 × ¥13.50 = ¥27.00
```

同一任务放在闲时窗口，输出成本减半。前提是业务本身可延迟——离线批处理、夜间报表、内容预生成都属此类；在线对话不属此类。

## 四、成本可控的四个杠杆

| 杠杆 | 具体做法 | 典型降本幅度 | 代价 |
|---|---|---|---|
| 模型分层 | 高频简单请求走小模型，复杂推理才上旗舰 | 大（示例 A/B 差 2.5 倍） | 需要按任务分类，工程上要维护路由 |
| 前缀稳定化 | 把 system prompt、工具定义等固定内容放在请求最前、保持不变 | 中（命中缓存约按输入价 1/10 计） | 提示词结构需重构，不能动态拼接前缀 |
| 输出收敛 | 限制 max_tokens、要求结构化输出、避免模型复述题干 | 中（输出单价普遍是输入的 5 倍） | 需要 prompt 约束与后处理校验 |
| 峰谷调度 | 可延迟任务移到闲时窗口执行 | 中（部分厂商闲时价为高峰 50%） | 牺牲时效，需要任务队列支持 |

四个杠杆互不冲突，可以叠加。落地顺序建议按「模型分层 → 输出收敛 → 峰谷调度 → 前缀稳定化」推进，因为前两项只改代码、不改业务节奏。

## 五、企业侧常见追问

**Q：为什么不做一张「全网最低价」对比表？**
因为价格随时变、口径随时改（峰谷、缓存、促销、阶梯），任何一张静态对比表在发布当天就开始失真。本页选择只呈现**带日期和来源**的少数条目，并在开源仓里持续维护，读者可自行 diff。

**Q：预算怎么报？**
用「月请求量 × 单请求 tokens 结构 × 单价」算出基线，再乘一个 1.3~1.5 的弹性系数应对重试、上下文膨胀与调价。不要用「上个月账单 × 增长率」这种外推法，它对结构变化毫无抵抗力。
